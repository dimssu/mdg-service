# mdg-guide — the Dealer Kavach video guide

The videos from `mdg-demo` published at **guide.mdgservices.in**. Public, no login.
Hindi and English side by side. The dealer and team videos are narrated in Hindi;
the public ones come in both languages. 66 videos today.

## Why it is built this way

The audience is fuel-pump dealers on cheap Android phones, often on 2G/3G. Every
decision below follows from that:

- **No framework, no build step worth the name.** Pages are generated as plain HTML
  by `scripts/build.mjs`. There is no React, no router, no client-side rendering.
- **CSS and JS are inlined into every page.** A watch page is about 13 kB gzipped
  and the dashboard about 21 kB, with no second request for a stylesheet. On a slow
  link, saving round-trips beats sharing a cached stylesheet across pages.
- **No webfonts.** Devanagari comes from the phone's own font, so text paints
  immediately and costs nothing.
- **Nothing downloads until you press play.** `preload="none"` plus a poster image
  means a watch page costs its HTML and a poster of 8 to 17 kB (five dealer-course
  videos run 21 to 41 kB). The video is only fetched on tap.
- **Three renditions, not adaptive streaming.** Each video is encoded at three
  rungs: tiny (240p, about 62 kbps, an emergency floor for 2G), low (360p, about
  90 kbps) and high (720p). The source is synthetic UI, flat colour and mostly
  static, so the Hindi captions stay legible even at the bottom. The player picks
  the rung itself from the connection and from how full its buffer is, and
  switches without losing the viewer's place. There is no quality picker, by
  design: a dealer would only be guessing at his bandwidth. HLS was measured and
  rejected, because hls.js is 106 kB gzipped even in its light build, roughly 17
  seconds of 2G before the first byte of video.
- **The library is small enough for that to work.** 66 videos, about 37 MB at the
  tiny rung, 58 MB at 360p and 149 MB at 720p.
- **Media filenames are content-hashed**, so they are served `immutable`: a video
  you have already watched is never re-downloaded, and a re-render can never be
  served stale.
- **Save to phone.** Every video can be downloaded and watched with no internet.

## Layout

```
content.mjs          bilingual copy for the hand-written videos, the UI strings,
                     the audiences; spreads in data/declared-videos.json
data/videos.json     generated: durations, frame size + orientation, byte sizes,
                     hashed URLs, chapter offsets
data/declared-videos.json  generated by `npm run guide:entries` in mdg-demo: the
                     copy for the 26 explainers in both languages (52 entries),
                     written inside the videos
public/media/        generated: tiny/low/high .mp4, poster.webp, thumb.webp, og.jpg
src/styles.css, search.css        inlined into the pages that use them
src/shell.js         language toggle, on every page
src/dash.js, progress.js          what this phone remembers it has watched
src/search.js        library search (dashboard)
src/player.js        sharing, chapters, automatic quality (watch pages)
scripts/build.mjs    generates dist/
scripts/serve.mjs    local preview (mirrors Vercel's cleanUrls + byte ranges)
scripts/kb-corpus.mjs   one page per video for the website assistant's knowledge base
```

## Working on it

```bash
npm run dev        # build + preview on http://localhost:4321
npm run build      # -> dist/
vercel --prod      # deploy
```

The videos and posters in `public/media/` are committed, so a deploy needs no
ffmpeg and no Remotion. To regenerate them after re-rendering the videos:

```bash
cd ..              # mdg-demo
npm run render     # or render:declared; re-render out/*.mp4 (needs the voiceovers)
npm run guide:media -- --only <id>[,<id>]
```

`guide:media` encodes the three rungs, cuts the posters, and measures each scene's
voiceover to place the chapter timestamps exactly on the video's scene cuts. **Always
pass `--only`.** Every file name carries a hash of its bytes, so a full run
re-encodes every video, gives every file a new name, and makes every dealer
download the whole library again. Ids are the tutorial ids, with the language for a
declared video (`gen-dod-clock-hi`, `gen-dod-clock-en`).

**Serving the media from S3 instead of git.** Set `GUIDE_MEDIA_BASE` when building
and every media URL is re-pointed at that base (`npm run media:push` in `mdg-demo`
prints the exact value). The security headers in `vercel.json` already allow the
`mdg-chat` S3 bucket. Unset, media is served from `public/media/` as above. Which of
the two the live deploy uses is set in the Vercel project and is not recorded here.

## Three audiences

Every entry carries an `audience`, and the dashboard shows them in this order:

- `'dealer'`: the numbered course, **भाग 1…N** (8 videos). This is the site's main
  promise and its numbering is load-bearing: nothing may be inserted into the
  middle of it.
- `'public'`: "Running a pump" / पंप की जानकारी (54 videos: the two marketing films
  and the 26 trade explainers, each in two languages). They teach the trade, not
  the app, are made to be forwarded to anyone, and never show an MDG screen. They
  are not numbered, since there is no order to take them in.
- `'admin'`: a separate labelled section ("एडमिन के लिए / For the MDG team", 4
  videos) outside the numbering, each card tagged **टीम / Team**. They walk through
  the internal ops portal, so they are left out of the sitemap, disallowed in
  `robots.txt` and marked `noindex`. That keeps crawlers out; it is not access
  control, so anyone with the link can still watch. Search on the site still finds
  them, so an admin can find one without knowing where it lives.

Prev/next paging stays inside a section, so nobody pages out of their own material.

Admin videos are also **landscape** (1920x1080: they record a desktop portal, not a
phone). That is handled end to end: `build-guide-media.mts` ffprobes each master and
encodes a matching ladder (portrait 240x426 / 360x640 / 720x1280, landscape
426x240 / 640x360 / 1280x720), writing `orientation`, `width` and `height` into
`data/videos.json`; the site sizes the card thumbnail and the player from those.
Nothing is ever squashed.

## Adding a video

Pick the path by how the video was written in `mdg-demo` (its README has both).

**Declared as data** (a file in `src/beats/social/`):

1. Render it, then run `npm run guide:entries` in `mdg-demo`. That writes the site's
   title, description, keywords and chapter labels into
   `data/declared-videos.json` from the video itself. There is nothing to add to
   `content.mjs`.
2. `npm run guide:media -- --only <id>-hi,<id>-en` in `mdg-demo`.
3. `npm run build && vercel --prod`.

**Hand-written** (a component in `src/videos/`):

1. Add the tutorial to `../src/narration.ts` and render it. Portrait or landscape
   both work; nothing needs to be told which, it is measured.
2. `npm run guide:media -- --only <id>` in `mdg-demo`.
3. Add a bilingual entry to `content.mjs` with an `audience` (`'dealer'` or
   `'admin'`; omitted means dealer). The `chapters` keys must match the scene ids in
   `narration.ts`; any that don't match are dropped silently.
4. `npm run build && vercel --prod`.

An entry whose media has not been generated yet is skipped with a warning rather
than failing the build, so a video can be written before it is rendered. Run
`GUIDE_STRICT=1 npm run build` to turn that back into a hard error, which is worth
doing before a deploy.

## The assistant's knowledge base

`npm run kb:corpus` writes one markdown page per video so the assistant on
mdgservices.in can point a visitor to the right video. It takes `dealer` and `public`
videos only and leaves the admin ones out on purpose: that assistant answers
strangers, and the admin videos describe how the work is done.
